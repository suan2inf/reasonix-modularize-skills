# Phase 3: 依赖图计算 + 波次调度

> 加载时机：Phase 2 完成后，或用户输入 `/schedule` 时

## 目标

根据模块依赖图计算拓扑排序，划分执行波次，生成可执行的调度计划。

## 前置条件

- `plan.json` 存在，status = `contracted`
- 所有模块的 contract.md 已就绪

## 执行流程

### Step 1: 读取依赖图

从 `plan.json` 读取模块列表和依赖关系。

### Step 2: 计算拓扑排序（Kahn 算法）

```
算法：
1. 计算每个模块的入度（有几个依赖）
2. 入度 = 0 的模块放入 Wave 0
3. 从图中移除 Wave 0 模块，更新余下模块的入度
4. 新入度 = 0 的模块放入 Wave 1
5. 重复直到所有模块分配完成
6. 如果还有模块剩余 → 存在循环依赖 → 报错
```

### Step 3: 展示调度计划

```
执行计划（共 4 波，最大并行度 2）：

┌──────────────────────────────────────┐
│ Wave 0 (可并行)                       │
│   ├── database      [无依赖]          │
│   └── storage       [无依赖]          │
├──────────────────────────────────────┤
│ Wave 1                                │
│   └── auth          等待: database    │
├──────────────────────────────────────┤
│ Wave 2                                │
│   └── api           等待: auth, storage│
├──────────────────────────────────────┤
│ Wave 3                                │
│   └── frontend      等待: api         │
└──────────────────────────────────────┘

确认？回复 "OK" 开始执行，或回复 "/schedule" 重新计算。
```

### Step 4: 写入调度结果

更新 `plan.json`：

```json
{
  "waves": [
    { "wave": 0, "modules": ["database", "storage"], "status": "pending" },
    { "wave": 1, "modules": ["auth"], "status": "pending" },
    { "wave": 2, "modules": ["api"], "status": "pending" },
    { "wave": 3, "modules": ["frontend"], "status": "pending" }
  ],
  "status": "ready"
}
```

### Step 5: 告知下一步

```
调度计划已就绪。

下一步：
- /execute-all → 从 Wave 0 开始依次执行全部模块
- /execute <模块名> → 手动执行单个模块
```

## 循环依赖检测

如果发现循环依赖（如 A 依赖 B，B 依赖 A），提示：

```
⚠️ 检测到循环依赖：auth ↔ api

循环依赖无法调度。请重新审视这两个模块的职责边界：
- 或许应该把共享部分抽离为第三个模块？
- 或许其中一个模块的接口可以用回调/事件解耦？

当前无法继续，请调整 plan.json 中的依赖关系后重试 /schedule。
```

## 递归拆分的调度

如果 plan.json 包含 `sub_modules`，子模块的调度独立计算，但整个父模块作为一个整体占据波次位置：

- 父模块标记为 single module 放入某个 Wave
- 执行到该 Wave 时，按子模块的波次依次执行
- 全部子模块完成后，父模块才标记为完成
